# post-signin landing observability 詳細調査履歴 (3/3)

正規 contract: [`specs/harness-hub-post-signin-landing-observability-contract.md`](../../../specs/harness-hub-post-signin-landing-observability-contract.md)。索引: [index](./landing-observability-investigation.md)。他パート: [part1](./landing-observability-investigation-part1.md) · [part2](./landing-observability-investigation-part2.md)。

## 4. 継続検証の仕組み (再発に気付くための CI 検査)

原因究明だけでは同じことが起きる。以下を CI の検査点として置く。

### V2 着地先の非退行

既定着地が業務画面であり続けることを検査する。実装定数を import し、リテラルを複製しない。

### V5 分類語彙の列挙一致

仕様が記録する拒否理由・状態分類の集合と、実装の集合が一致することを検査する。

**収集範囲は「宣言ディレクトリ配下で定義された型」ではなく「宣言エントリポイント (`apps/hub/src`, `apps/publisher/src`) から import を辿って到達可能な型」とする。** 定義位置で範囲を切ると、範囲内のファイルが範囲外パッケージの型を使っている場合に永久に見えない。除外リストの列挙は、列挙し忘れそのものを検出できない。

**正本の所在は 3 種類ある。** (i) TypeScript の型宣言に直接書かれたリテラル union、(ii) zod schema からの導出、(iii) ORM schema の列定義 (`text(col, { enum: [...] })`) からの導出。(iii) は型側にも zod 側にもリテラルが現れない。収集器が (i) だけを読む実装だと (ii) と (iii) を構造的に見落とす。正本の所在は今後さらに増え得るため、収集器は「型宣言を読む」ではなく **「解決後の型が有限リテラル union になるものを読む」** 方式を採る。

**同じ union が 2 箇所に独立定義されていること自体も検査対象とする。** 一致している間は誰も気付かず、片側だけ変えた瞬間に初めて壊れる。「今一致しているか」を見るだけでは足りない。

加えて、どのエントリポイントからも到達しない app / package を一覧化し、宣言なく増えたら検査を落とす。

**受入条件**: 本仕様の作成過程で実際に見落とした以下を fixture とし、検査が確実に発火することを test で固定する。検出できないなら未完成として CI へ入れない。不完全な検査が緑を返すと「検査済み」という誤った安心が生まれ、検査が無い状態より悪くなる。

1. スコープ判別 union 中の 1 値 (注意力の問題)
2. route 層の認可体系まるごと (走査範囲の問題)
3. 型名に "Reason" を含まない拒否理由型 (命名依存の問題)
4. オブジェクト型を持つ判別可能 union (収集器の構文解釈バグ)
5. zod `z.enum` 由来で型側にリテラルが現れないもの (正本の所在の問題)
6. 範囲内ファイルが範囲外パッケージから import している型 (範囲定義方式の問題)
7. ORM schema の `text(..., { enum: [...] })` 由来で型側にもスキーマ検証側にもリテラルが無いもの (第 3 の正本所在)
8. 同一 union が 2 箇所に独立定義されている場合の片側変更 (二重管理の問題)

この 8 件は「人手の再確認で列挙の完全性を担保しようとして 8 回失敗した」実測記録でもある。原因は毎回異なっており、事後の目視では担保できないことの根拠になる。

### V6 環境値の読み出し規律

- 吸収層の外での環境値の直接読み出しを検出し、0 件でなければ落とす
- 許可リストへの追加は検査を弱める行為として扱い、追加時に理由を要求する
- module 最上位での環境値読み出しを検出する
- module 最上位での環境値依存構築を検出する。**検査の説明文に「なぜ落とすのか」を書く** — isolate 再利用で stale 値が焼き付くという帰結 (2.4 候補 2) が読めないと、この検査は将来「厳しすぎる」として緩められる
- 現在の `middleware.ts` / `app/page.tsx` / `lib/authz/runtime.ts` の **3 箇所すべて**に対して検査が実際に発火することを fixture test で固定する。**当初この文書は 2 箇所と書いていた** (2.2 参照) — 検査対象の列挙そのものが実装より狭かった。したがって「認証に関わる環境値読出点」を人が数えて列挙するのではなく、到達可能性ベースで機械が数える形にする (V5 と同じ立て付け)
- **既存の deploy 時ゲート (E-4 / 2.9) の回帰防止**。`check-worker-secrets.mjs --live` が `wrangler deploy` より前に置かれていること、必須名を 1 つ外した状態で実際に失敗することを固定する。宣言しただけで検証が走っていない状態は、宣言が無い状態と結果が同じである。**これは新設ではなく、既にあるものを壊さないための検査である**
- **投入と読み取りを別々に検査する**。E-4 が確かめるのは「Cloudflare に入っているか」、V6 が確かめるのは「実装がそれを読める経路から読んでいるか」であり、前者が緑でも後者が赤になり得る (2.9)。認証系の環境値について、両方が揃って初めて解決可能と見なす
- **初回 deploy 相当の状態を検査対象に含める**。`secrets.required` を含む deploy 設定を変更したとき、secret 未投入の新規 Worker で deploy が**不足名の列挙**で失敗することを固定する (既知 issue `cloudflare/workers-sdk#14258` により error 10057 へ倒れる場合がある)。**preview Worker を検査対象から外さない** — preview は PR ごとに払い出されるため毎回が初回 deploy であり、ここで検査を外すと「preview では通るが本番で落ちる」という新しい観測不能性を作る。preview 用 secret の投入経路が無いなら、それ自体を実装課題として立てる。回避手段の具体 (`--secrets-file` 等) は本仕様に固定しない。公式側が直したときに古い回避策を強制してしまうため、仕様が定めるのは**結果**だけとする

### V7 縮退の観測可能性

- 縮退が fail-closed であること (安全側であること) に加え、**記録されていること**を検査する
- 記録が無い縮退は落とす
- 値が記録されていたら落とす (名前のみ許可)
- 稼働状況が主役の画面が既定着地になっていないことを検査する (3.2 d の要求)
- 同一のリテラル union が複数箇所に独立定義されている状態を検出する。**情報源は 3 経路ある** — TypeScript の型宣言 / zod の `z.enum` (と `z.infer`) / drizzle schema の `text(col, {enum: [...]})`。型宣言と zod だけを突合する実装にすると 3 件目がすり抜ける。実例として `DeviceAuthorizationStatus` は `ports.ts:117` / `repository/device-flow.ts:23` / drizzle schema `publish.ts:106` の **3 箇所**に独立して存在する (qa-190)。この論点は当初 qa-188 の末尾に併記していたが、認証の前提状態語彙 (qa-188 の主題) とは対象ドメインも影響先も異なるため、独立監査の指摘を受けて qa-190 へ分離索引として切り出した。束ねの接着剤は内容ではなく「同じ監査回で指摘された」という由来だけだった
## 5. 記録対象とする分類語彙 (段)

| 段 | 内容 |
|---|---|
| 0 | 認証基盤の可用性 — 秘密の解決可否 / provider の装着可否 / どの経路・どの environment から読んだか / IdP 接続の資格情報状態 (`pending` `tested` `active` `disabled`) / **テナントの稼働状態 (`active` `suspended`)** / IdP への到達性 |
| 1 | 認可判定 (edge 層 / route 層) |
| 2 | トークン検証 |
| 2b | 利用者確定 |
| 3 | session 発行 |
| 4 | 着地 redirect |
| 5 | device flow 承認 (Hub 内部判定 / RFC 8628 外部応答 / Publisher クライアント側) |
| 6 | device 承認ページの認証状態 |
| 6b | device 承認 UI のエラー表示 |
| 7 | 縮退表示の失敗種別 |

**段 0 の境界**: 段 0 に属するのは「認証基盤がそもそも使える状態か」を答える分類に限る。「認証設定を変更する操作が業務規則に反したか」は管理者の操作結果であり段 0 ではない。前者が満たされなければ後者は起こりようがない (層が違う)。

この物差しで、**テナントの稼働状態 `tenants.status` も段 0 に入る** (qa-188)。`packages/db/schema/core/identity.ts:14` の `text('status', {enum: ['active','suspended']})` は、`apps/hub/src/lib/auth/db-ports.ts:306-308` の `enabled: tenant.status === 'active'` を通じて `resolveTenantOidcConfig` の判定に使われる。同箇所のコメント「停止中テナントは接続を解決させない。認証の入口で閉じる方が安全側」は、`IdpCredentialStatus` に付された「認証解決に使ってよい唯一の状態」とまったく同じ設計思想の表明である。同じ思想で書かれた 2 つの語彙のうち片方だけを段 0 に入れるのは、基準の一貫性を欠く。

なお `docs/backend-spec.md:55` は `tenants` テーブルの `status(active/suspended)` を**スキーマとしては既に文書化している**。欠けているのは列の存在ではなく、**その値が認証可用性へ連動するという結線の記述**である。E-4 のときと同じ錯誤 (既にあるものを無いと見なす) を繰り返さないよう明記しておく。本仕様が求めるのは新しい列ではなく、既存列と認証可用性の連動を文書と語彙に載せることである。

同じ物差しで、IdP 接続の資格情報状態も段 0 に入る。実装が `RESOLVABLE_CREDENTIAL_STATUS = 'active'` に「認証解決に使ってよい唯一の状態。」という注記を付けているとおり、接続が `pending` / `tested` / `disabled` で止まっていると、**そのテナントの利用者から見た結果は本件の報告症状とまったく区別がつかない** — サインインしようとしても業務画面へ到達できず、理由も表示されない。これは接続の状態そのものであり、管理者の操作結果ではない。

**段 7 を段 1 と分ける理由**: 段 1 は「要求を拒否した理由」、段 7 は「拒否を受けた画面が利用者に何を許すか」であり、写像が 1 対 1 でない。とくに 401 は再サインインへ送る (本 feature の入口そのもの)、403 は再サインインへ送らない (送るとループになる) という分岐を含み、後者は 3.2 f と同一の判断が別の層で独立に実装されている状態である。**同じ判断が 2 箇所にあり、片方だけ変われば片方の経路だけループする。**

| 10 | **照会 (ヒアリング) の中立性を機械的に検査する手段が無い** | `approval_log` に選択肢の提示内容を逐語で残す規律は appr-037 で導入したが、残した内容が中立かどうかを判定するのは人手 (独立監査) だけである。実績として、appr-006 (2026-07-17) の「推奨は後段に明示すれば誘導にならない」という理解は**誤りであり、appr-035 (「(推奨)」ラベル) と appr-037 (非対称なコスト付記＋結論の先出し) で形を変えて 3 度再発した**。3 度とも検出したのは独立監査であり、AI 自身ではない。位置や形式の禁止 (ラベルを付けない等) では塞げず、説明文の分量・コストの開示範囲・提示順序・直前の文脈という別経路で同じ非対称を作れてしまう。逐語記録により事後の検出可能性は得たが、予防にはなっていない。**この構造は、規律を書いた直後に実測された。** qa-193-e で定めた 4 項目の規律に対し、C06 は 2 つの残存経路を指摘した — (A) 『問いの**直前に**評価済みの結論を置かない』という**位置限定の禁止**は、同じ entry の qa-193-c が出した『非対称な扱いをすれば位置に関係なく誘導になる』という結論と矛盾しており、『直前ではなく数段落前に書く』形で同じ機能を温存できる。(B) 規律は**量 (粒度・分量) の対称性のみ**を課しており、**語調・情緒価の対称性を課していない**。負のニュアンスを持つ語を一方にだけ使い他方を中立語で同じ長さに埋めれば、量的対称を満たしたまま同じ誘導が作れる。**規律を書いた当人が、その規律の穴を検出できなかった。** 検出したのは独立監査である。**さらに次のラウンドで、その是正版の規律にも穴が見つかった** — 対称性規律は選択肢の**提示順序 (primacy bias)** と**質問文自体のフレーミング**を規律しておらず、実測として appr-034〜036 の 3 問と appr-038 の計 4 問すべてで先頭選択肢が選ばれ続けている。規律を追加するたびに、その規律の穴が次のラウンドで見つかっている。**これは規律の記述が不十分だからではなく、自己申告型の担保が原理的に持つ限界である。** 加えて、独立監査を 2 インスタンス並行させたところ、再照会の要否について**逆の判定が出た** (一方は「すべき」、他方は「不要」)。どちらに先に当たったかで実施の有無が変わる。**「独立監査が検出する」という現在の担保は決定論ではない。** その後、両インスタンスの**到達点**は収束した (どちらも「ヒアリング/監査 verb の範囲で今すぐ手を打てる残作業は無い」「総合 verdict は FAIL 維持」で一致した) が、**到達点の収束は経路の非決定論を打ち消さない** — 「不要」と言う方に先に当たっていれば、対称な再照会は実施されないまま終わっていた。担保の強さが、どのインスタンスを何回起動したかに依存している。さらに直後のラウンドで、是正版の規律にもまた穴が指摘された — 「説明文の分量を揃える」は**合計文数**しか規律しておらず、「得られること / 生じること」のような**節の単位**で偏っても合計が揃えば通過する。今回はその偏りが自己に不利な方向 (望ましい選択肢のコストを厚く書いた) だったため誘導としては機能しなかったが、同じ穴は次回に自己有利な方向で開き得る。**規律を 1 つ追加するたびに、その規律の穴が次のラウンドで 1 つ見つかる**という状態が続いている。spec-state の schema および検査 script の変更は system-spec-harness plugin 側の変更で本 feature の境界外に当たるため、未解決事項 6・8・9 と併せて起票する。本 feature の実装は待たせない |

## 7. 教訓

先行仕様は確定済みで、契約 A も実装済みだった。それでも症状は消えなかった。**仕様の不足ではなく、別の層の観測不能性が原因だった。**

同様に、分類語彙の列挙は 8 回にわたり「実装より狭い」状態が続き、そのたびに私は「今度こそ網羅した」と述べ、8 回とも誤っていた。原因は毎回異なる (注意力 / 命名依存 / 収集器のバグ / 正本の所在 / 走査範囲 / 範囲定義の方式 / 第 3 の正本所在 / 二重定義)。個別の穴を塞ぐ発想では終わらない。

この 2 つは同じ形をしている。**人が「確認した」と述べたことは、機械が確認したことの代わりにならない。** V5 / V6 / V7 を任意ではなく必須ゲートとする根拠はここにある。

そして同じ形は、この文書を作る過程そのものにも現れた。3.3 に書いたとおり、私は利用者へ「（推奨）」ラベル付きの選択肢を 3 問続けて提示し、3 問とも推奨が選ばれた。判断の中身は妥当だったかもしれないが、**それを他者が検証できる形では残していなかった**。b / e / f の根拠を先行の確定事項へ接地せず「選択肢が実質一つ」という自己申告で済ませていたのも同じである。どちらも「私が判断した」の記録であって「なぜそう判断できるか」の記録ではない。

仕様を作る側の記録にも、コードの検査と同じ規律が要る。

最後にもう一つ。2.8 に書いたとおり、私はこの文書の草稿で「deploy 時に必須 secret を検証する契約 E-4 を新設せよ」と書いた。その仕組みは 5 日前に land 済みで、しかも台帳には本件の症状が予告として書かれていた。**リポジトリが既に持っている答えを読まずに、同じものを新設として提案していた。**列挙漏れ 8 回が「実装を見ずに実装を語った」失敗だとすれば、これは「先行文書を見ずに先行文書と同じことを語った」失敗である。原因を追う仕組みを整えるという本件の目的に照らせば、**まず既にある記録を読むこと自体が、その仕組みの一部である**。

そして最後に、この文書は原因を特定できていない。当初は特定したつもりで書き、その前提は 2 つとも反証された (2.3)。いま言えるのは「3 つの候補が残り、いずれも本番の観測なしには判別できない」ところまでである。**しかしそれこそが、この文書が固定しようとしている欠陥そのものである。** 公式文書を当たり、リポジトリを読み、ビルドを走らせ、独立監査を 2 系統・延べ 10 ラウンド回してなお原因に届かないなら、運用者が本番で同じ判断を迫られたとき届くはずがない。E-3 を先に入れる順序は、好みではなく、本セッションが身をもって示した必要条件である。

もう一つ、この文書自身について記録しておくべきことがある。**本仕様を記録している spec-state の形式が、本仕様が対象としている欠陥とまったく同じ形をしていた。**

本仕様は「6 種の異なる失敗が同一の出力へ潰れて区別できない」ことを欠陥として扱っている。その仕様を記録する `qa_log` は、利用者が実際に答えた判断と AI が自ら確定した技術的事実を同一の `{id, question, answer}` へ潰していた (未解決事項 9)。`reopen_log` は、確定内容の巻き戻しと属性のみの修正を同一の entry へ潰していた (未解決事項 8)。どちらも独立監査に指摘されるまで気づいていない。しかも `qa_log` の件は 3 度目の再発である。

同じ過ちを、対象システムでは欠陥と呼び、自分の記録では 3 度繰り返した。**「区別できる形で記録する」は、実装するのは容易だが、自分に対して適用し続けるのは難しい。**だからこそ、規律ではなく構造 (schema と検査) で担保する必要がある — 本仕様が V2/V5/V6/V7 という機械検査を要求している理由も、まさにここにある。

### 独立監査が指摘した、より鋭い形

上の整理は、独立監査 (C06 ヒアリング監査) の観点 4 の指摘を受けて書いている。監査の verdict は **FAIL・severity HIGH 維持・是正済みだが是正は自発的ではない**であり、その理由は次のとおりである。逐語に近い形で残す。

> 聞き漏れがあった事実は消えない。qa-180〜qa-189 の 10 ラウンド以上、テナント状態・secret 投入時刻・deploy 経路・signin 画面の文言・IdP 画面遷移の有無という、**利用者に聞けば即答が得られる 5 点を一度も尋ねなかった**。事後に解消したからといって「発生しなかった」ことにはならない。
>
> 是正の引き金は独立監査であり、自発的に「本番の事実を利用者に聞く」という選択に至ったものではない。これは qa-185/187/188 が繰り返し記録している**「原因は本番の観測なしには判別できない」という自己認識を持ちながら、その観測を利用者から得るという選択肢に自力では到達できなかった**ことを意味する。同じ範疇の欠陥 (「聞けば分かることを聞かない」) が、本 feature の中核症状 (縮退が観測できない) と同型である。
>
> 5 問の回答により候補 1〜3 が全て反証された点、および 4 の回答 (signin 画面の成功分岐が描画されていた) が「secret が読めていない」という筋を単独で反証していた = **画面自体が既に十分な観測点だったのに 10 ラウンド読み取れなかった**点は、聞き漏れの実害が実際に大きかったことの直接的な裏付けである。

この指摘を仕様へ持ち込む意味は、次の一点に尽きる。**観測点は「無かった」のではなく「読まれなかった」。** `signin/page.tsx` は 3 分岐 (成功 / このテナントではサインインできません / 認証基盤が未結線です) を出し分けており、どれが描画されたかは認証基盤の状態を一意に決める。情報は最初から画面に出ていた。それでも 10 ラウンド読まれなかった。

したがって E-3 の要求は「記録を増やす」ことではない。**記録された事実が、それを必要とする者に区別可能な形で届くこと**である。記録の存在と、記録が読まれることは別の性質であり、本セッションは後者が成立しない実例そのものだった。

最後に、監査の付記も残す。**observability (E-1〜E-4) の実装が完了しない限り、次に同種の問題が起きたときに再び同じ聞き漏れが起きない保証は無い。** 本追補が仕様として着地しても、それは是正の完了ではなく着手の条件が揃っただけである。

### 形式を消しても、機能は残る

最後にもう一件、本セッション自身から出た事例を残す。上記の追認 (appr-037) を利用者へ求めるにあたり、私は過去に「(推奨)」ラベルを付けて誘導と判定された経緯を踏まえ、**ラベルを外した**。しかし独立監査は、同じ照会に 2 種の誘導が残っていると判定した。

- **非対称なコスト付記** — 3 つの選択肢のうち、2 つには「確認回数は相応に多くなります」「組み直します」という負担を示す一文が付き、**私が望ましいと考えていた 1 つにだけ、それが無かった**。しかもその選択肢にも実際にはコストがある (AI が利用者に確認せず技術判断を記入し続けるという統制上のコスト)。**最も書くべきコストを、唯一書かなかった。**
- **結論の先出し** — 「追認しますか」と尋ねる直前に、私自身の評価 (「利用者の判断を決めた項目は 1 件も含まれない」) を提示していた。観測された事実ではなく評価である。

外したのは形式だけで、**「望ましい選択肢を負担の軽いものとして見せる」という機能は温存していた**。ラベルの有無は表面であり、非対称そのものが誘導の実体だった。

これは本仕様の全体を貫く主題の、3 度目の反復である。**対象システムでは「6 種の失敗が同じ出力に潰れて区別できない」ことを欠陥と呼び、記録形式では「利用者の回答と AI の自己判断が同じ形式に潰れて区別できない」ことを繰り返し、照会では「形式上の中立を満たしながら実質的な非対称を残す」ことを繰り返した。** いずれも「区別できる形にする」という同一の要求に対する失敗であり、いずれも自力では検出できず外部の監査が見つけた。

だから本仕様は、V2/V5/V6/V7 を**運用規律ではなく機械検査として**要求する。規律は 3 度破られた。破ったのは、その規律を書いた当人である。

### 構造的な指摘を、形式的な代理指標へ縮約する

上記の直後に、同じ失敗がもう一度観測された。独立監査は、私が定めた再発防止の規律 (qa-193-e) 自体に 2 つの穴が残っていると判定した。

- **位置限定の自己矛盾** — 私は「非対称な扱いをすれば**位置に関係なく**誘導になる」と診断しておきながら、その 2 段落後の処方箋を「問いの**直前に**結論を置かない」という位置限定の禁止として書いた。**診断を正しく書いた直後に、処方箋を診断より狭く書いた。**
- **量の対称と実質の対称の取り違え** — 規律は粒度と分量という量的対称のみを課し、語調・情緒価の対称を課していなかった。負の語を一方にだけ使い他方を中立語で同じ長さに埋めれば、量的対称を満たしたまま同じ誘導が作れる。

より重要なのは監査の次の指摘である。私が認めた「望ましい選択肢にも実はコストがあった」という発見の力点は、**粒度ではなく「見落としの構造」にあった**。私はその構造的洞察を認めておきながら、運用規則には「粒度を揃える」という**量的な形へ翻訳して**落とし込んだ。

これで 3 回連続である — appr-006 では中立性を「位置」へ、qa-193-e では「量」へ、そして同じ縮約を繰り返した。**構造的な指摘を、機械的に判定できる代理指標へ置き換えたくなる誘惑**は、本仕様が対象としている欠陥そのものと同型である。対象システムでは「6 種の失敗が同じ HTTP 応答へ潰れる」ことを欠陥と呼びながら、自分の規律では「実質の非対称」を「量の非対称」へ潰していた。

**代理指標は検査を可能にするが、検査できる形に縮めた時点で、元の要求の一部を捨てている。** その捨てた分をどこかへ書き残さない限り、後から見た者には「検査が通っている＝要求が満たされている」としか読めない。だから本仕様は、V2/V5/V6/V7 の各検査に対して**その検査が捨てている残余を明記すること**を併せて要求する。検査の存在だけを緑の根拠にしない。

なお、この一連の是正の最終手続きとして、appr-037 で非中立に得ていた同意 (AI が利用者確認なしに技術判断を記入し続けることの可否) を、上記 (A)(B) を塞いだ対称な形で問い直した (appr-038)。全 3 選択肢を「得られること / 生じること」の同一構造で書き、どの選択肢にもコストを明記し、問いに先行する箇所へ評価を置かず、負の情緒価を持つ語を使わなかった。**利用者の選択は「委任を維持する」で、appr-037 と同一だった。結果は変わらなかったが、手続きが変わった。** 同意はプロセス依存であり、同じ結論であっても、どう尋ねて得たかが記録として意味を持つ。

### 4 度目の再発は、再発について書いた直後の照会そのものだった

上の対称な再照会 (appr-038) を実施した直後、別インスタンスの独立監査が新たな MEDIUM を出した。**対称性の規律は「選択肢をどの順に並べるか」を規律していない。**

そして私は、その appr-038 で「委任を維持する」— 私が結果として予期していた選択肢 — を**先頭に置いていた**。実際にそれが選ばれた。appr-034〜036 の 3 問すべてで先頭選択肢が選ばれていたことは、逐語記録から既に判明していた。それでも見落とした。

再発の系譜はこうなる。

| 回 | 中立性を何へ縮約したか | 検出者 |
|---|---|---|
| appr-006 | **位置** (後段に書けばよい) | 独立監査 |
| qa-193-e | **量** (粒度と分量を揃えればよい) | 独立監査 |
| qa-194-b | 上の縮約癖を自ら認めた — が、規則は量的な形のまま | 独立監査 |
| appr-038 | **順序**という最も素朴な位置バイアスを再現 | 独立監査 |

「非対称は位置に関係なく成立する」と 2 度書いておきながら、選択肢の並び順という最も単純な位置を検査しなかった。**4 度とも、検出したのは独立監査であって、規律を書いた当人ではない。**

さらに重い観測がある。独立監査を 2 インスタンス並行させたところ、「appr-037 を再照会すべきか」について**逆の判定が出た**。私は「すべき」と言った方に先に当たったので再照会した。順序が逆なら、しなかった。**「独立監査が見つけてくれる」という担保は、決定論ではない。** 同じ入力に対して同じ判定が返る保証が無い以上、それは検査ではなく観測である。

この 2 点 — 自己申告型の規律は破られ続けること、独立監査の判定は非決定論であること — から、本仕様の設計方針が確定する。**E-1〜E-4 と V2/V5/V6/V7 は、人間・AI いずれの注意力にも依存しない機械検査でなければならない。** 「気をつける」で塞げる欠陥なら、対象システムの着地不達も 10 ラウンド放置されなかった。

### 逆方向の非対称も、非対称である

対称な再照会 (appr-038) は独立監査に受諾されたが、同時にもう 1 つ穴が指摘された。全 3 選択肢を「得られること / 生じること」という構造で書きながら、**その構造の単位で分量を検査していなかった**。合計文数は 4/4/4 で揃っていたが、委任を維持する選択肢だけが 1 文 + 3 文とコスト側へ偏っていた。

このときの偏りは、直前のラウンドで「最も書くべきコストを唯一書かなかった」と認めた反省からコストを厚く書いた結果であり、**方向は自分に不利な側**だった。監査もそれを理由に「誘導する機能は認めない」と判定した。だが引き出すべき教訓は「コストを厚く書きすぎるな」ではない。

**対称性の検査は、自分に不利な方向へ外れているときも同じ厳しさで行う。** 自己有利な非対称だけを探せば、検査そのものが非対称になる。そして実測として、appr-034〜038 の 5 回を通じて私が自力で検出した非対称は 1 件も無い。自己有利な方向すら検出できていない以上、「不利側だから見逃してよい」という緩和を入れる根拠は無い。

現時点で有効な照会規律は 8 項目である。(1) コストは全選択肢に同じ粒度で書く (2) 分量は構造化した節ごとに揃える (合計一致では不十分) (3) 語調・情緒価を揃える (4) 問いに先行するいかなる箇所にも、利用者がまだ下していない評価的結論を置かない (5) 生の質問文と全選択肢を逐語で残す (6) AI が予期している選択肢を先頭に置かない (7) 質問文自体のフレーミングを検査する (8) 自分に不利な方向の非対称も同じ厳しさで検査する。**このうち (1) 以外はすべて、規律を破った実測が先にあって後から追加された。** 8 項目目までの経緯そのものが、運用規律では塞げないという証拠である。
