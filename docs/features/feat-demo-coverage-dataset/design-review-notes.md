# 確認用データセット 設計レビュー記録

## 1. 判定

**承認 (approved)。P04 のテスト設計へ着手してよい。**

第 1 周のレビューで 2 論点に不適合を認め、`architecture-decision-record.md` へ反映を求めた。反映後の第 2 周で 4 論点すべてが適合した。

## 2. レビューの方法と独立性の限界

本レビューは、設計文書の記述をそのまま受け取らず、記述が参照する実体 (schema 定義・既存 seed 実装・画面コード・画面定数) を独立に再測定して突き合わせる方法で行った。

独立性については限界がある。本レビューは P02 の設計を作成したのと同一のセッションが実施しており、別担当者による独立レビューではない。この限界を、実測との突合という機械的な検証で部分的に補っている。人による独立レビューが別途必要と判断された場合は、本記録を入力として実施できる。

## 3. 論点ごとの判定

### 3.1 論点 1: 28 route × 5 状態対応表の未カバー 0 件方針 — 適合 (pass)

| 検証 | 結果 |
|---|---|
| 対応表の行数が実測 route 数と一致するか | 一致 (`page.tsx` 実測 28 件 = 対応表 28 行 = 画面台帳の現行行 28 件) |
| 140 セルに未記入が無いか | 適用 105 / 非適用 35 / 未記入 0 |
| 非適用に理由が付いているか | 全 35 セルが N1〜N7 のいずれかを持つ |
| 非適用理由が実体と合っているか | `/legal` に対する N3 (データ取得を伴わない) を検証し、当該画面がデータ取得を行っていないことを確認した |
| 動的 route の扱いが定義されているか | ADR §2.2 の `ReachStep.url` が「動的 route は実際の識別子まで解決済みとする」と定めており、route 定義と実体の区別が付いている |

未カバー 0 件を宣言ではなく検査 (ADR §9.2 の検査 1・2) で担保する構成になっており、方針として十分である。

### 3.2 論点 2: enum 全値網羅方式 — 第 1 周 不適合 → 反映後 適合 (pass)

#### 第 1 周の指摘

**指摘 A: 動作前提と衝突する enum 値の扱いが未定義。**

`tenants.status` の `suspended`、`users.status` の `inactive`、`idpConnections.credential_status` の `disabled` は、「テナント `local` が有効で、seed した利用者でサインインできる」という既存 seed の前提と衝突する。既存行の値を書き換えて網羅を満たすと、全画面へ到達できなくなり、受入条件 A1 (28 route × 5 状態への到達) を満たせない。A2 と A1 が両立しない設計のまま P05 へ渡ると、実装段階で seed の構造をやり直すことになる。

**指摘 B: 画面に現れないテーブルの扱いが未定義。**

`encryptionKeys` / `smokeFixtureLeases` / `auditEvents.actor_type` / `buildStageEvents` などは 28 route のいずれにも表示されない。受入条件 A2 は画面表示の有無で対象を絞っていないため投入対象に含まれるはずだが、設計上その位置づけが述べられていなかった。実装者が「画面に出ないから不要」と解釈する余地が残っていた。

#### 反映内容の確認

ADR に §10.1 (動作前提と衝突する enum 値の扱い) と §10.2 (画面に現れないテーブルの enum) が追加された。前者は主テナントとは別に停止状態の副テナントを持つ構成を定め、後者は投入対象に含めたうえで画面到達手順を持たないことを明示している。指摘 A・B はいずれも解消した。

なお §10.1 の帰結として対象テナントが 2 件になるため、削除条件がテナント境界を含むという制約 (ADR §4.3) は 2 件それぞれに適用される。この点も反映済みである。

#### その他の確認

| 検証 | 結果 |
|---|---|
| enum 一覧が実測と一致するか | 40 カラム / 129 値が `packages/db/schema/**` の実測と一致 |
| 上流仕様との差分が記録されているか | 正本 task spec は enum を core 2 ファイル (9 カラム) に限定していたが、受入条件 A2 は限定を含まない。実測 40 カラムを正本とする判断が `requirements-baseline.md` §7.14 に記録されている |

### 3.3 論点 3: 冪等性の実現方式 — 第 1 周 不適合 → 反映後 適合 (pass)

#### 第 1 周の指摘

**指摘 C: 新規に扱うテーブルの削除順が未定義。**

既存 `seed-local.ts` が扱うのは 15 テーブルであり、その削除順は実測として ADR に記録されていた。一方 enum 129 値を網羅するには 14 テーブルを新たに扱う必要がある (`builds` / `buildStageEvents` / `packages` / `deploymentReferences` / `deviceAuthorizations` / `encryptionKeys` / `smokeFixtureLeases` / `documents` / `feedbacks` / `aiJobs` / `hearingShareTokens` / `metricsRollups` / `notionIntegrations` / `tenantDataObjects`)。この 14 テーブルの外部キー依存順が定まっておらず、実装者が順序を推測する余地が残っていた。削除順を誤ると外部キー制約で実行が落ちるか、削除漏れが冪等性を壊す。

**指摘 D: 論理キー衝突の検証方法が未定義。**

決定論 ID の要件 R3 は「異なる論理キーが同じ ID へ衝突しない」と述べていたが、これは宣言では担保できない。導出方式が固定長へ写像する以上、衝突の可能性は構造的に存在する。検証手段が無いまま「衝突しない」と書くのは、確認していない事柄を確認済みとして扱うことになる。

#### 反映内容の確認

ADR に §4.1.1 (新規に扱うテーブルと削除順の決め方) が追加され、削除順を人手で並べず schema の外部キー参照関係から位相順序で導出する規則 (O1〜O4) が定められた。順序が一意に定まらない場合の安定化と、循環時の停止も規定されている。指摘 C は解消した。

ADR に §3.3 (論理キー衝突の検証) が追加され、全論理キーから導出した ID の集合の要素数が論理キー件数と一致することを検査する方式が定められた。検査は §9.2 の検査 7 として検査コマンドに組み込まれる。指摘 D は解消した。

#### その他の確認

| 検証 | 結果 |
|---|---|
| 既存の削除順の記載が実測と一致するか | 一致 (`seed-local.ts` の削除呼び出し順と同一) |
| 非決定性の発生源が列挙されているか | ID (§3.2)・時刻 (§3.4)・削除範囲・テナント境界の 4 点が ADR §4.3 に列挙され、それぞれに防ぎ方が対応している |
| 既存の ID 生成との関係が整理されているか | 実行時の `newUlid()` は乱数依存のため冪等性を満たさないこと、seed 専用の導出を新設し実行時コードは置き換えないことが明記されている |

### 3.4 論点 4: ローカル専用ガード非緩和 — 適合 (pass)

| 検証 | 結果 |
|---|---|
| 既存ガードを再利用する方針か | `isLocalDatabaseUrl` をそのまま呼び出す方針で、判定の再実装を明示的に禁じている (G4) |
| 判定の位置が正しいか | 投入処理より前に判定し、拒否時は DB へ一切書き込まない (G1) |
| 終了コードが既存と一致するか | 2 で一致 (既存実装の実測値と同じ) |
| 迂回経路の追加が禁じられているか | 環境変数・オプション・デバッグ経路の追加を禁じている (G3) |
| 許可される URL の形が実測と一致するか | `file:` / `http://127.0.0.1` / `http://localhost` の 3 種で一致 |

判定が二重化すると片方だけ緩む余地が生まれる、という理由づけが G4 に添えられており、方針の根拠が明確である。本 feature は削除 → 再投入を行うためガードが破れたときの被害が既存 seed 以上になるという認識も、ADR §8.3 に記録されている。
