**一貫性の判定:** 矛盾なし。特に注目したのは P03 の指摘 C・D で、これは「冪等性を設計方針として宣言したが、実現手段 (削除順) が未定だったため実装者に推測の余地が残る」という**方針と手段の落差**を捉えたものである。落差が放置されていれば P06 で偶然 pass しても、テーブル追加時に静かに壊れる。反映後の ADR §4 に 29 テーブル分の削除順が実測として記録されており、落差は閉じている。

### 2.2 C-2: ローカル以外の DB URL 拒否

| P04 検査設計 | 拒否 (T4-1)・書き込み 0 (T4-2)・**ローカル URL が誤って拒否されない** (T4-3)・判定の非再実装を静的検査 (T4-4)。URL 判定は他のどの引数検査よりも先に行う契約 | T4 |
| P06 実行 | T4 4 件 pass。`libsql://` は exit 2、`file:` は exit 0 の実測 | — |
| P07 受入 | A6 pass | — |
| P09 品質 | G7 pass | G7 |

**一貫性の判定:** 矛盾なし。この constraint で最も効いているのは T4-3 と T4-4 の組合せである。T4-1 だけなら「常に拒否する」実装で緑になってしまい、T4-3 がそれを塞ぐ。T4-4 は G4 の「再実装しない」を静的検査へ翻訳したもので、**設計方針が検査可能な形へ落ちている数少ない例**である。方針が文章のままで検査に落ちていなければ、後から誰かが `seed-coverage.ts` に URL 判定を書き足しても誰も気づかない。

CLI の引数解釈順 (URL 判定が最先) も P04 §4 で契約化され、実装 `seed-coverage.ts` の §S1 が従っている。この順序が後ろにあると「URL を拒否したのか他の引数が足りなかったのか」をテストが区別できず、exit 2 の意味が曖昧になる。

## 5. 判定の限界

- 本レビューは記述内容とデータ内容に基づく判定であり、実際にブラウザで 28 画面を開いて表示崩れがないことは確認していない。それは本 feature の scope 外 (デモデータの整備が目的であり、画面上の崩れの是正は別 scope) である。
- C-1 の冪等性は「同じ入力に対する 2 回実行」で検査している。スキーマ変更を挟んだ実行や、他プロセスと同時に走らせた場合の性質は検査対象に含まない。
- C-2 のガードは URL 文字列の形に基づく判定である。ローカルに見える URL がトンネル経由で外部 DB を指す構成は防げない。これは既存 `seed-local.ts` と同じ前提であり、本 feature が新たに導入した弱点ではない。
