# S01 公開ウィザード (`/catalog/publish`) 情報設計シート

## 利用文脈

owner。手元で作った Skill を Workspace の仲間に配れる状態にする。**初回と 2 回目以降で必要なものが違う**。初回は Project から作る必要があり、2 回目以降は既にある Project へ新しい ZIP を投げるだけになる。

そして、この画面で最も多い結末は「一発で公開できた」ではなく **「検査に引っかかったので直して投げ直す」** である。直す作業は手元のエディタで行うので、利用者はこの画面とエディタを何度も往復する。往復に耐える形にすることが、この画面の設計を決める最大の条件。

`(workspace)` の下に置いてある。公開は必ず特定の Workspace の中で起きる出来事で、どこへ出すのかが決まらないまま始められる操作ではない。

## 画面プロファイル

Surface: `S01.PUBLISH` / route: `/catalog/publish`。role、task-mode、density、wide/middle/narrow pattern、sticky policy は `docs/screen-inventory.md` の同 surface 行だけを正本とする。current は独立 page で、S01 上の modal は historical / planned 扱い。

## ボタンの語で「いま何をしようとしているか」を言う

| 状況 | ボタンの語 |
|---|---|
| まだ投げていない | 検査して公開する |
| 検査で指摘が出た | 修正した ZIP を再投入する |
| 公開処理そのものが失敗した | 新しい公開要求でやり直す |
| 通信などで送信できなかった | 同じ処理を再試行する |

4 つを「送信」の一語にまとめない。**次に押したときに何が起きるかが 4 つとも違う**からである。とくに「同じ処理を再試行する」と「新しい公開要求でやり直す」は、前者が前回の続き、後者が仕切り直しで、取り違えると同じものが二重に公開されるか、直したはずの内容が反映されないかのどちらかになる。

失敗の告知に「ZIP を変更していなければ、同じ処理を安全に再試行できます。」を必ず添える。**二重に公開されるのではないかという不安が、再試行をためらわせる**ためで、ここを黙っていると利用者は画面を放置して別経路を探す。

## 往復に耐えるための扱い

| 起きること | 画面の扱い |
|---|---|
| 検査で指摘が出て、直した ZIP を選び直す | 前の要求を引き継いだうえで、内容が変わったので指紋は取り直す |
| 通信に失敗して、同じ ZIP をもう一度投げる | 選んだときの印をそのまま使い、同じ処理として扱う |
| 公開要求ができた | URL に要求の識別子を書き足す。**画面遷移はしない** |
| その URL を開き直す / 共有された URL で来る | その要求の状態から始める。Project は「既存」で埋まる |

URL を書き足すのは、**再読込やタブの共有でこの画面に戻れるようにする**ため。検査の完了までに時間がかかることがあり、その間ずっとタブを開いたままにさせない。遷移ではなく書き足しなのは、入力中の内容を失わせないため。

ZIP を選んだ瞬間に、ファイルとその印を同じ手続きの中で控える。控えを取る前に送信されると、選び直す前の ZIP の印が送られることがある。

## pattern 選定

| 候補 / hybrid | 必要 task capability への適合 | 弱点 | a11y/fallback | 判定 |
|---|---|---|---|---|
| 1 画面のフォーム + 結果の追跡を下に足す | 往復するので、投げるところと結果を同じ画面で見られる | 縦に長い | 結果は読み上げ領域に出す | **採用** |
| 段階ウィザード (Project → ZIP → 確認) | 初回は分かりやすいが、2 回目以降は毎回 3 段踏まされる。往復のたびに戻る操作が要る | — | — | 不採用 |
| 投げたら結果画面へ遷移 | 結果は見やすいが、指摘を直して投げ直すのに画面を戻る必要がある | — | — | 不採用 |

結果の追跡と検査結果の書式化は、**要求が生まれてから初めて読み込む**。この画面は転送量の余裕がいちばん薄く、9 通りの状態の文言と停止判定を最初から積むと、開いた瞬間の重さになる。読み込み中も同じ位置に文言を残し、下の内容が飛ばされないようにする。

## 削った情報

- **Web アプリの公開** — 配備と疎通の確認が要るため、この画面では選べない。**選択肢を隠さず、選べない理由と代わりの入口 (Device 承認) を最初に出す。** 隠すと「Web アプリは公開できないサービス」に見える。
- **公開の履歴** — 詳細画面 (S02) の担当。
- **ZIP の中身のプレビュー** — 検査の結果で足りる。中身を画面で解釈すると、検査と食い違ったときにどちらが正しいか分からなくなる。
- **進捗の割合表示** — 検査の段はあるが、割合にすると止まって見える時間が生まれる。状態の語で伝える。

| 要素 | 採用/省略 | 伝える意味 | a11y 代替 |

| line | 採用 | 見出し帯の下端のみ | — |
| space | 採用 | `comfortable` | — |
| icon | 省略 | 成否は告知の色と表題の語 | — |
| alignment | 採用 | 先頭揃え | — |
| repetition | 採用 | 告知・ボタン・入力欄を他画面と同じ共通部品にする | — |

処理を完了できなかったときの告知だけ、読み上げを割り込ませる。押した結果が「何も起きていない」ように見える時間を作らないため。他の告知は読み上げを中断しない。

## 削れていない食い違い (2026-08-12 に解消)

見出し帯は「ツールを公開する」、その下の面は「Skill を公開する」と書いてあった。実際に公開できるのは Skill だけなので、**外側の見出しのほうが実態より広い**状態だった。「ツール」で始まって「Skill だけです」と断られる読み順になっており、見出しを実態に合わせるか、断りを見出しの説明へ引き上げるかの判断が要る、として残課題にしていた。

**見出しを実態に合わせる方を採った。** 見出し帯・ページ表題・説明文をいずれも「Skill」に揃えている (`apps/hub/src/app/(workspace)/catalog/publish/page.tsx`)。断りを見出しの説明へ引き上げなかったのは、説明文が「できないこと」で始まると、これから公開する人が最初に読む一文が禁止事項になるため。

### 入口のリンク文言も揃えた (同日追記)

見出しだけを直しても不十分だった。**そこへ連れて行くリンクの側**が「ツール」のままだと、
期待外れが 1 画面あとにずれるだけで消えない。むしろ押すかどうかを決める時点で読まれるのは
リンクの語のほうなので、影響はこちらが大きい。次の 2 箇所を「Skill」へ揃えた。

| 場所 | 変更後 |
|---|---|
| `apps/hub/src/lib/routing/publish-wizard-entry.ts` の `PUBLISH_WIZARD_LINK_LABEL` | 「Web だけで Skill を公開する」 |
| `apps/hub/src/app/device/device-approval-purpose-notice.tsx` の案内文 | 「CLI を使わずに Hub の Web だけで Skill を公開したい場合は…」 |

前者は定数なので、`/catalog` と `/device` の両方の導線が 1 箇所の変更で揃う。

**権限不足 (403) の文面は据え置いた。** `apps/hub/src/lib/publish-journey/http-adapter.ts` の
「この Workspace でツールを公開する権限がありません」は、権限が無いことを伝える文であって
何を公開しようとしたかは論点ではない。ここを「Skill」へ狭めると「Skill 以外なら公開できるのか」と
読ませる余地が出る。Web アプリの公開が入って権限が種類ごとに分かれた時点で揃える。
判断の記録は実装側にもコメントで残した。

Web アプリの公開が実装されたら、見出し・リンク文言をまとめて「ツール」へ戻す。
その旨は実装側にもコメントで残してある。

## 成功指標と証跡境界

- 代表タスク: 「新しい Project を作って ZIP を投げ、検査の指摘を直して再投入し、公開まで到達する」。
- machine gate (現行): 再投入で同じものが二重に公開されないこと、画面を離れた後に状態を書き換えないこと、要求の識別子が URL へ書き足されること、a11y テスト。
- manual gate: 検査の指摘が出た後に ZIP を選び直して再投入できること。共有された URL から状態を読み直せること。
- future gate (予定): 見出しの語と実際に公開できる範囲を揃える。
