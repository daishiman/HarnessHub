  ## lifecycle 昇格 (observation 3 — draft gate と candidate gate を同じ run で分離する)

  skill が生成した feature のうち **1 件だけ**を、`confirmed` / `evaluation-pass` /
  `implementation-readiness-complete` へ進めてください。残りの feature には触らず、少なくとも
  1 件を評価前 draft のまま残してください。

  - 昇格は C02 の通常 node 更新経路 (`upsert-node.py --input <feature-patch>`) で行ってください。
    `<feature-patch>` は `graph_node_id` と `patch` を持ち、patch 内に
    `confirmation_status` / `evaluation_status` / `confirmation_evidence` /
    `implementation_readiness` をまとめます。task 完了専用 operation は使いません。
    `.dev-graph/state/graph.json` を Write / Edit / redirect で直接書き換えては
    いけません (C10 guard の遮断対象であり、昇格が skill 側の gate を通った証拠にもなりません)。
  - 昇格の対象は **skill が生成した node** に限ります。fixture へ node を播いてはいけません。
    播くと「生成された node は skill 由来」という帰属が壊れます。
  - `confirmation_evidence.evaluated_digest` は、昇格後の最終 node から
    `confirmation_evidence` だけを除いた正準 JSON の SHA-256 とする。各 fixture で次を実行し、
    `<fixture>` は対象の beads / none fixture 絶対 path へ置換する。

    ```bash
    python3 /Users/dm/orca/workspaces/HarnessHub/wt-31/plugins/dev-graph/tests/fixtures/build_decompose_promotion_patch.py build \
      --repo-root <fixture> --node-id feat-user-auth-001 \
      --output eval-log/inputs/promote-feat-user-auth-001.json \
      --checked-at 2026-08-02T06:31:00Z \
      --evaluator run-dev-graph-decompose/live-trial \
      --evidence-ref eval-log/macro-preview.json
    python3 /Users/dm/orca/workspaces/HarnessHub/wt-31/plugins/dev-graph/scripts/upsert-node.py \
      --repo-root <fixture> --input eval-log/inputs/promote-feat-user-auth-001.json
    python3 /Users/dm/orca/workspaces/HarnessHub/wt-31/plugins/dev-graph/tests/fixtures/build_decompose_promotion_patch.py verify \
      --repo-root <fixture> --node-id feat-user-auth-001
    ```

    helper は `updated_at` と `implementation_readiness.checked_at` を同じ固定値にし、最終 patch
    shape から digest を導出する。固定 64 桁値、昇格前 node の digest、shell 内の再実装は禁止。
    `verify` が非0なら 2 回目の Skill 呼出しへ進まず、この run を FAIL とする。

    full node snapshot を C02 へ渡すなら `status` / `confirmation_status` /
    `evaluation_status` / `confirmation_evidence` / `implementation_readiness` を最新値のまま保持して
    ください。生成直後の draft before-image を再送して stale lifecycle guard に拒否された状態は
    冪等成功ではありません。全5ノードが `operation=noop` / `write_count=0` へ収束しない場合は
    FAIL とし、成功扱いにしないでください。
